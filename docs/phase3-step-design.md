# Phase 3 단계별 개발 설계: 선택지를 비교하며 정하기

[Phase 3 개념 문서](phase3-api-server-concepts.md) 가 "무엇을 알아야 하나" 라면, 이 문서는 **"어떤 순서로, 무엇을 골라서 만들 것인가"** 를 정한다.

> **결정은 읽는 사람이 한다.** 문서의 **[추천]** 은 이유와 함께 낸 의견일 뿐 결정이 아니다. 결정은 각 항목의 **`[내 선택]`** 칸과 맨 아래 [결정 기록](#7-결정-기록)의 **내 선택** 열에만 적는다. 칸이 `미정` 이면 아직 정하지 않은 것이다.

---

## 0. 이 문서를 읽는 법

각 단계는 같은 틀로 쓴다.

| 항목          | 내용                          |
| ----------- | --------------------------- |
| **목표**      | 이 단계가 끝나면 무엇이 되는가 (한 문장)    |
| **결정**      | 선택지 표. **[추천]** 은 의견, **[내 선택]** 칸이 실제 결정 |
| **완료 기준**   | 눈으로 확인할 수 있는 합격 조건 (명령어 포함) |
| **하지 않는 것** | 일부러 뒤로 미룬 것. 범위가 번지는 것을 막는다 |

선택지는 **버리는 이유**까지 적는다. 나중에 "왜 이걸 안 썼지?" 를 다시 따지지 않기 위해서다.

로드맵·완료 기준은 **추천 선택을 가정**하고 썼다. 다르게 고르면 그 단계의 완료 기준도 같이 고친다.

## 1. 단계를 어떻게 자를 것인가 (첫 번째 결정)

| 선택지                       | 방식                                              | 장점                                                      | 단점                                           |
| ------------------------- | ----------------------------------------------- | ------------------------------------------------------- | -------------------------------------------- |
| A. 계층별 (가로)               | 소켓 전부 → HTTP 전부 → JSON 전부 → 스레드 전부              | 계층마다 깊게 만든다                                             | 끝까지 가야 처음으로 `curl` 이 동작한다. 중간에 방향이 틀려도 늦게 안다 |
| **[추천] B. 기능별 (세로 슬라이스)** | 가장 단순한 서버가 **끝에서 끝까지** 돌게 한 뒤, 한 번에 한 가지씩 교체·보강 | 매 단계가 `curl` 로 확인된다. 항상 "동작하는 서버" 가 있다. PR 을 작게 쪼갤 수 있다 | 초반 코드를 나중에 고치게 된다 (의도된 것)                    |
| C. 병렬 분업                  | 사람마다 계층을 맡아 동시에                                 | 빠르다                                                     | 인터페이스가 먼저 정해져야 한다. 합칠 때 터진다                  |

**추천 이유 (B)**: 이 과제의 핵심 위험은 **동시성**이다. 동시성은 "단일 스레드 서버가 먼저 정확히 돌아갈 때" 만 의미 있게 테스트된다. B 는 단일 스레드 정확성(S1~S3)을 먼저 못 박고, 그 위에서 동시성(S4~S5)을 얹는다. 락을 뺀 버전과 넣은 버전을 비교할 기준선도 생긴다.

> C 는 S1~S3 이 끝난 뒤 **S4 와 S5 의 조사**, **S6 의 부가 기능** 정도에서만 부분적으로 쓴다.

> **[내 선택]** B

## 2. 전체 로드맵

```
S0 엔진 연결 지점 정리 ─▶ S1 반복 서버 + /health ─▶ S2 /query (단일 스레드)
                                                          │
                       S5 rwlock ◀─ S4 스레드 풀 + 전역 락 ◀─ S3 HTTP 견고성
                           │
                           └──▶ S6 마감 (종료·부가 API) ─▶ S7 측정·문서·발표
```

| 단계  | 한 줄                                | 병렬성       | 새로 배우는 것                     | PR 단위             |
| --- | ---------------------------------- | --------- | ---------------------------- | ----------------- |
| S0  | 서버가 엔진을 부를 수 있게 정리                 | 없음        | 빌드·모듈 경계                     | `refactor:`       |
| S1  | 소켓으로 `/health` 응답                  | 없음        | socket, bind, listen, accept | `feat:`           |
| S2  | `POST /query` 가 SQL 을 실행하고 JSON 반환 | 없음        | HTTP 파싱, JSON 이스케이프, 상태 코드   | `feat:`           |
| S3  | 큰 요청·느린 클라이언트·끊김에 안 죽기             | 없음        | recv/send 루프, 타임아웃, SIGPIPE  | `feat:` + `test:` |
| S4  | 스레드 풀 + 전역 락                       | 시작        | mutex, condvar, 생산자–소비자      | `feat:` + `test:` |
| S5  | 읽기-쓰기 락                            | SELECT 병렬 | rwlock, 공유 자원 감사             | `feat:` + `test:` |
| S6  | graceful shutdown, 부가 엔드포인트        |           | 시그널, join                    | `feat:`           |
| S7  | 성능 비교표, 문서                         |           | 측정 방법                        | `docs:`           |

브랜치는 [README](../README.md#5-브랜치-전략) 의 규칙대로 `feat/<이름>-<기능>` → `develop` 으로 **단계마다 PR 하나**를 연다.

## 3. S0 — 엔진과 서버를 잇는 지점 정리

**목표**: 서버 코드를 얹어도 기존 CLI·테스트가 그대로 돌아가는 상태를 만든다.

현재 코드에서 걸리는 지점 세 가지를 먼저 확인했다.

| 걸리는 지점 | 위치 | 왜 문제인가 |
|---|---|---|
| `src/*.c` 를 전부 한 바이너리로 링크 | [Makefile](../Makefile) `$(BIN): $(SRCS)` | 서버 `main()` 을 `src/` 에 두면 CLI 의 `main()` 과 충돌 |
| 여러 문장 실행 로직이 `main.c` 의 `static` 함수 | [main.c](../src/main.c) `run_sql` / `run_statement` | 서버가 부를 수 없다 |
| `db_get_table` 이 테이블을 **처음 쓸 때** 연다 | [db.c](../src/db.c) | 두 스레드가 동시에 처음 열면 `tables[]` 에 중복 등록 |

### 결정 01-. 서버 `main()` 을 어디에 둘까

| 선택지                                         | 장점                                                     | 단점 / 버리는 이유                                           |
| ------------------------------------------- | ------------------------------------------------------ | ----------------------------------------------------- |
| a. `src/server_main.c`                      | 파일 하나만 추가                                              | Makefile 이 `src/*.c` 전부를 CLI 에 링크하므로 `main` 이 두 개가 된다 |
| **[추천] b. `server/` 디렉터리 + Makefile 타겟 추가** | 엔진(`src/`)은 건드리지 않는다. 서버가 엔진 라이브러리 소스(`LIB_SRCS`)만 재사용 | Makefile 을 고쳐야 한다 (`-pthread`, 새 타겟)                  |
| c. `main.c` 에 `--serve` 옵션                  | 파일이 늘지 않는다                                             | CLI 코드와 서버 코드가 섞인다. 테스트에서 분리하기 어렵다                    |

**추천 이유**: 이미 `LIB_SRCS := src/*.c - main.c` 로 "엔진 = main 을 뺀 것" 이라는 경계가 있다. b 는 그 경계를 그대로 확장한다.

> **[내 선택]** B

### 결정 0-2. 문장 실행 로직(`run_sql`) 재사용

| 선택지                                      | 장점                          | 단점 / 버리는 이유                         |
| ---------------------------------------- | --------------------------- | ----------------------------------- |
| a. 서버에 복사                                | 빠르다                         | 두 벌을 따로 고치게 된다                      |
| **[추천] b. 공용 모듈로 추출** (`src/runner.c` 등) | CLI·서버가 같은 경로를 탄다. 한 곳만 테스트 | 리팩터가 먼저 필요하고, 출력 콜백을 인자로 받도록 바꿔야 한다 |
| c. 서버는 한 문장만 처리                          | 추출이 필요 없다                   | 결정 2-4 에서 다문장 정책을 막아 버린다            |

**추천 이유**: Phase 1 에서 "전역 변수 금지, 결과는 콜백" 규칙을 둔 덕분에 추출이 쉽다 (`print_row` 자리에 `json_row_cb` 를 꽂으면 된다). 추출 전후의 CLI 출력이 같아야 하므로 **기존 `make test` 가 곧 회귀 테스트**다.

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

### 결정 0-3. 테이블 지연 오픈(lazy open) 경쟁

| 선택지 | 장점 | 단점 / 버리는 이유 |
|---|---|---|
| **[추천] a. 서버 시작 시 `data/*.schema` 를 모두 미리 연다** | 이후 `tables[]` 는 읽기만 하는 구조. 엔진 수정 없음 | 서버 실행 중 새 테이블 파일을 추가하면 인식 못 함 (README 가 이미 "실행 중 `data/` 직접 수정 금지" 를 요구) |
| b. `db_get_table` 만 별도 mutex 로 보호 | 새 테이블도 즉시 사용 | 모든 요청이 이 mutex 를 거친다. 엔진 코드에 락이 들어간다 |
| c. 엔진에 동기화를 내장 | 호출자가 신경 쓸 게 없다 | 엔진이 스레드를 알게 된다. 단일 스레드 CLI 가 락 비용을 낸다 |

**추천 이유**: `Db.tables[8]` 이 고정 배열이라 "처음 연다" 가 곧 "배열을 수정한다" 이다. 시작 시 한 번에 열어 두면 S5 의 rwlock 에서 SELECT 가 `tables[]` 를 건드리지 않는다는 근거도 얻는다.

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

**완료 기준**
- `make test` 전부 통과, CLI(`./build/mini-dbms queries.sql`) 출력이 리팩터 전과 동일
- `make server` (이름은 팀 결정) 가 빈 `main()` 으로라도 빌드된다

**하지 않는 것**: 엔진에 락 넣기, 새 SQL 기능 추가

## 4. S1 — 반복 서버와 `/health`

**목표**: `curl http://127.0.0.1:8080/health` 가 `{"ok":true}` 를 돌려준다. 스레드 없이 `accept → 처리 → close` 만 반복.

### 결정 1-1. HTTP 를 어떻게 다룰까

| 선택지 | 장점 | 단점 / 버리는 이유 |
|---|---|---|
| **[추천] a. 직접 구현** (socket + 최소 HTTP 파서) | 의존성 없음. 소켓·TCP 바이트 스트림·`Content-Length` 를 직접 겪는 것이 학습 목표. Docker 이미지 변경 불필요 | 코드량이 늘고, 파서 버그를 우리가 책임진다 |
| b. libmicrohttpd 등 라이브러리 | 파싱·견고성이 검증되어 있다 | 스레드 모델을 라이브러리가 쥐어서 **스레드 풀을 직접 만드는 과제 요구와 겹친다**. Dockerfile 수정 필요 |
| c. 프로토콜을 HTTP 가 아닌 전용 TCP 로 | 파서가 단순 | `curl`·브라우저·Postman 으로 못 부른다 (개념 문서 6.1) |

**추천 이유**: 과제가 소켓·TCP 바이트 스트림·`Content-Length` 를 직접 다루는 학습이다. 라이브러리는 스레드 모델을 쥐고 있어 "스레드 풀을 직접 만든다"는 요구와 겹치고, Dockerfile 도 바꿔야 한다.

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

### 결정 1-2. 지원할 HTTP 범위

| 선택지 | 장점 | 단점 |
|---|---|---|
| **[추천] a. HTTP/1.1, 요청 하나당 연결 하나 (`Connection: close`)** | 요청의 끝 = 연결의 끝. 상태가 없어 단순 | 연결 재사용 불가 → 부하 테스트 시 연결 비용이 섞임 |
| b. Keep-Alive 지원 | 현실적인 성능 | 한 연결에 여러 요청 → 요청 경계·타임아웃이 복잡. 스레드 풀과 결합하면 한 연결이 worker 를 점유 |

**추천 이유**: Keep-Alive 는 S4 이후 풀 고갈 문제와 얽힌다. 뒤로 미룬다.

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

### 결정 1-3. 바인드 주소

| 선택지 | 이유 |
|---|---|
| **[추천] a. `127.0.0.1` 기본, 인자로 변경 가능** | 인증이 없는 DB 를 기본으로 외부에 열지 않는다 |
| b. `0.0.0.0` 고정 | Docker 포트 매핑 시 컨테이너 밖에서 접근 불가해질 수 있어 필요한 경우가 있다 → 인자로 해결 |

> Docker 로 띄울 때는 컨테이너 안에서 `127.0.0.1` 로 바인드하면 호스트에서 접근이 안 된다. `compose.yaml` 포트 매핑과 함께 `--bind 0.0.0.0` 을 쓴다.

**추천 이유**: 인증이 없는 DB 를 기본으로 바깥에 열지 않기 위해서다. Docker 에서 호스트로 접근해야 할 때만 `--bind 0.0.0.0` 을 쓰면 된다.

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

**완료 기준**
```sh
curl -i http://127.0.0.1:8080/health     # 200, {"ok":true}
curl -i http://127.0.0.1:8080/nope       # 404
curl -i -X POST http://127.0.0.1:8080/health   # 405
```
- 서버를 껐다 바로 다시 켜도 `Address already in use` 가 없다 (`SO_REUSEADDR`)

**하지 않는 것**: `/query`, 스레드, 타임아웃

## 5. S2 ~ S3 — 단일 스레드에서 정확하게 만들기

### S2. `POST /query` 가 엔진을 지나 JSON 으로 돌아온다

**목표**: `curl -X POST .../query --data-binary "SELECT * FROM users;"` 가 JSON 을 돌려준다. 엔진을 부르는 부분은 [개념 문서 11.5](phase3-api-server-concepts.md#115-요청-하나가-엔진을-지나는-길) 의 흐름을 따른다.

#### 결정 2-1. 요청 본문 형식

| 선택지 | 장점 | 단점 |
|---|---|---|
| **[추천] a. `text/plain` SQL 원문** | 본문을 그대로 토크나이저에 넘긴다. JSON **입력** 파서가 필요 없다 | SQL 에 `"` 가 있어도 상관없지만 메타데이터를 못 싣는다 |
| b. `{"sql":"..."}` | 표준적인 모양 | C 로 JSON 입력 파서·언이스케이프를 만들어야 한다 |
| c. 둘 다 | 편의 | 구현·테스트가 두 배 |

**추천 이유**: JSON **출력** 이스케이프만으로도 충분히 어렵다. b 는 S6 의 선택 과제로 미룬다.

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

#### 결정 2-2. JSON 을 어떻게 만들까

| 선택지 | 장점 | 단점 |
|---|---|---|
| **[추천] a. 직접 문자열 버퍼에 쓰기 + 이스케이프 함수** | 의존성 없음. 콜백이 행마다 버퍼에 이어 붙이는 구조와 잘 맞는다 | 이스케이프(`"`, `\`, 제어문자)를 빠뜨리면 JSON 이 깨진다 → **단위 테스트 필수** |
| b. cJSON 등 라이브러리 | 이스케이프가 검증됨 | 행마다 객체를 만들었다 직렬화 → 메모리 두 배. Dockerfile 변경 |

**추천 이유**: 콜백이 행마다 버퍼에 이어 붙이는 구조와 맞다. 라이브러리는 행마다 객체를 만들었다 직렬화해서 메모리를 두 배로 쓴다. 이스케이프만 단위 테스트로 막으면 된다.

### S3. HTTP 견고성 — 이상한 클라이언트에게도 죽지 않기

**목표**: 개념 문서 12 의 함정 표를 **테스트로 하나씩 재현**하고 막는다. 이 단계를 스레드 이전에 하는 이유는, 풀을 도입한 뒤에는 "worker 하나가 멈춘다" 가 곧 서버 전체의 성능 저하이기 때문이다.

#### 결정 3-1. 읽기 타임아웃

| 선택지 | 장점 | 단점 |
|---|---|---|
| **[추천] a. `setsockopt(SO_RCVTIMEO)`** | 한 줄. `recv` 가 알아서 실패(`EAGAIN`) | 소켓 단위. 요청 전체의 총 시간 제한은 아니다 (조금씩 보내는 느린 공격은 못 막음) |

**추천 이유**: 한 줄로 끝나고, 풀 고갈의 가장 흔한 원인인 "아무것도 안 보내는 연결"(개념 문서 12)을 막는다. 총 시간 제한은 필요해질 때 추가하면 된다.

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

#### 결정 3-2. 크기 상한 (값은 팀이 정하고 상수로 문서화)

| 대상 | 제안 | 넘으면 |
|---|---|---|
| 요청 줄 + 헤더 | 8 KB | 431 또는 400 |
| 본문 (`Content-Length`) | 1 MB | 413 |

**추천 이유**: 숫자는 측정 근거가 없는 **제안값**이다. 상수 하나로 두고 바꿀 수 있게 하면 틀려도 비용이 작다. 메모리 고갈(`Content-Length: 99999999999`)을 막는 것이 핵심이다.

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

#### 결정 3-3. 끊어진 연결에 `send`

| 선택지 | 장점 | 단점 |
|---|---|---|
| **[추천] a. 시작 시 `signal(SIGPIPE, SIG_IGN)`** | 모든 경로를 한 번에 보호 | 프로세스 전역 설정 |
| b. `send(..., MSG_NOSIGNAL)` | 호출 단위로 명시적 | 빠뜨린 `write` 가 하나라도 있으면 서버가 죽는다 |

**추천 이유**: 시작할 때 한 번 설정하면 모든 `send`/`write` 경로가 보호된다. `MSG_NOSIGNAL` 은 호출마다 붙여야 해서 하나만 빠뜨려도 서버 전체가 죽는다.

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

**완료 기준** (`nc`/`curl` 로 각각 재현)
- 헤더를 `\r\n\r\n` 없이 일부만 보내고 멈춤 → 타임아웃 후 연결 정리, 다음 요청 정상
- `Content-Length: 99999999999` → 413, 메모리 증가 없음
- 응답 받는 도중 클라이언트 강제 종료 (`curl --max-time`) → 서버 생존
- 서버 로그에 fd 누수 없음 (`ls /proc/<pid>/fd | wc -l` 가 요청 후 원복)

**하지 않는 것**: 스레드, Keep-Alive

## 6. S4 ~ S7 — 동시성과 마감

### S4. 스레드 풀 + 전역 락 (동시성 1단계)

**목표**: worker N 개가 요청을 동시에 처리하되, 엔진 호출은 **락 하나**로 직렬화해서 데이터가 절대 깨지지 않는다.

#### 결정 4-1. 서버 모델

| 선택지 | 결과 |
|---|---|
| 반복 서버 (S1~S3 그대로) | 동시성 없음. 비교 기준선으로만 보존 |
| thread-per-request | 상한이 없어 과부하에 취약 |
| **[추천] 스레드 풀** | 과제 요구사항. 상한이 있고 큐로 과부하를 흡수 |

**추천 이유**: 과제 요구사항이다. 반복 서버는 비교 기준선으로만 남긴다.

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

#### 결정 4-2. 풀 크기

| 선택지 | 장점 | 단점 |
|---|---|---|
| **[추천] a. 고정 기본값(예: 4) + `--threads N` 인자** | S7 에서 1/2/4/8 을 바꿔 가며 측정할 수 있다 | 기본값이 맞는지는 측정 전엔 모른다 |
| b. CPU 코어 수 자동 | 편리 | 측정 재현성이 떨어진다 (Docker 에서는 코어 수가 호스트와 다르게 보이기도 함) |

**추천 이유**: S7 에서 스레드 수를 바꿔 가며 측정해야 하므로 인자가 필수다. Docker 에서는 보이는 코어 수가 호스트와 달라 자동 감지는 재현성이 낮다.

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

#### 결정 4-3. 작업 큐와 과부하 정책

| 큐 구현 | 장점 | 단점 |
|---|---|---|
| **[추천] 고정 크기 원형 배열** | 메모리 상한이 명확. 구현이 짧다 | 크기를 정해야 한다 |
| 연결 리스트 | 무제한 | 과부하 시 메모리 폭주 — 풀을 쓰는 이유가 사라진다 |

| 큐가 꽉 찼을 때 | 장점 | 단점 |
|---|---|---|
| **[추천] a. `503` 을 즉시 보내고 닫기** | 서버가 응답성을 유지. 클라이언트가 재시도 판단 가능 | main 스레드가 응답을 쓰는 동안 잠깐 막힌다 (작은 응답이라 허용) |
| b. main 이 빈 자리가 날 때까지 `accept` 를 멈춤 | 단순 | 커널 백로그가 차서 클라이언트는 연결 타임아웃 |

**추천 이유**: 큐에 상한이 있어야 풀을 쓰는 의미가 있다. 가득 찼을 때 즉시 `503` 을 주면 클라이언트가 원인을 안다. 조용히 닫으면 원인 불명이고, `accept` 를 멈추면 커널 백로그에서 클라이언트가 타임아웃을 맞는다.

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

**추천 이유**: 정확성을 먼저 확보해야 이후 rwlock 과 비교할 기준선이 생긴다 (개념 문서 10.3 도 같은 순서를 권한다).

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

#### 결정 4-5. 락을 잡는 구간

| 선택지 | 장점 | 단점 |
|---|---|---|
| **[추천] a. `execute()` 호출 구간만** | 락 보유 시간이 최소. **응답 `send` 전에 푼다** → 느린 클라이언트가 락을 붙잡지 않는다 | 결과를 락 안에서 버퍼에 완성해 둬야 한다 (결정 2-3 이 이미 만족) |
| b. 요청 처리 전체 | 실수할 여지가 적다 | 느린 클라이언트 하나가 전체 DB 를 멈춘다 |

**추천 이유**: 락 보유 시간을 최소로 하고, 느린 클라이언트 하나가 전체 DB 를 붙잡는 일을 막는다.

#### 결정 4-6. 풀이 쓰는 동기화 도구

**[추천]** `pthread_mutex_t` + `pthread_cond_t` (큐 not-empty / not-full). 세마포어 대안이 있다. **추천 이유**: 종료 신호(S6)로 잠든 worker 를 깨우기 쉽다. `pthread_cond_wait` 는 반드시 `while` 안에서 부른다 (스스로 점검 질문 6).

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

**완료 기준**
- 동시성 테스트: 100개 INSERT 를 동시에 → **100행, id 가 1..100 중복 없음** (개념 문서 13.3)
- **일부러 락을 뺀 빌드**에서 같은 테스트가 실패하는 것을 한 번 확인한다 (락이 실제로 필요하다는 증거. 발표 자료가 된다)
- `-fsanitize=thread` 빌드에서 경고 없음 (ASan 과 동시 사용 불가 → 별도 타겟)
- 큐를 일부러 작게 하고 폭주시키면 `503` 이 나오고 서버는 회복

**하지 않는 것**: rwlock, 테이블별 락

### S5. 읽기-쓰기 락 (동시성 2단계)

**목표**: SELECT 끼리는 동시에, INSERT 는 혼자서. 읽기 부하에서 처리량이 오른다는 것을 **수치로** 보인다.

#### 사전 조사 (코드로 확인한 사실)

"SELECT 는 읽기만 한다" 는 가정이 맞는지부터 확인해야 한다.

| 확인 대상 | 현재 코드 | 읽기 락 아래 안전한가 |
|---|---|---|
| `storage_scan` 등 읽기 경로가 쓰는 `open_for_read` | 먼저 `fflush(t->fp)` (쓰기용 FILE*) 호출 — [storage.c:181](../src/storage.c) | **아니다.** SELECT 가 쓰기 fp 를 건드린다 |
| `db_get_table` | 처음이면 `tables[]` 에 추가 | S0 의 미리 열기(0-3) 로 해결 |
| 읽기용 파일 핸들 | 호출마다 따로 연다 | 안전 |
| B+ 트리 탐색 | 읽기 전용 | 쓰기와 분리되면 안전 |

#### 결정 5-1. `fflush` 문제를 어떻게 풀까

| 선택지 | 장점 | 단점 |
|---|---|---|
| **[추천] a. INSERT 가 끝날 때(쓰기 락 안에서) 항상 `fflush`, 읽기 경로(`open_for_read`)에서는 `fflush` 하지 않음** | SELECT 경로가 진짜 읽기 전용이 된다 | 엔진 수정이 필요하다. INSERT 마다 flush 비용 (이미 SELECT 마다 하고 있으니 총량은 비슷) |
| b. `fflush` 전용 작은 mutex | 엔진 무수정 | 읽기 락 아래에서도 직렬화 지점이 생겨 병렬성이 줄고, "읽기 전용" 설명이 깨진다 |
| c. 읽기도 쓰기 락 | 문제 소멸 | rwlock 의 의미가 없어진다 |

**추천 이유**: SELECT 경로가 진짜 읽기 전용이어야 rwlock 의 전제가 성립한다. 별도 mutex 를 두면 읽기 병렬성이 줄고 "읽기 전용" 설명이 깨진다.

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

#### 결정 5-2. 락 granularity

| 선택지 | 장점 | 단점 |
|---|---|---|
| **[추천] a. DB 전체에 rwlock 하나** | 데드락 가능성이 없다. S4 에서 mutex → rwlock 로 **한 줄 교체** 수준 | 서로 다른 테이블의 INSERT 가 서로 막는다 |
| b. 테이블별 rwlock | 테이블 간 병렬성 | 락이 여러 개 → 획득 순서 규칙(데드락 방지) 필요. 현재 문장이 단일 테이블이라 이득이 작다 |

**추천 이유**: 락이 하나뿐이라 데드락 규칙이 필요 없고, S4 의 전역 mutex 에서 거의 한 줄 교체다. 현재 문장이 단일 테이블이라 테이블별 락의 이득도 작다.

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

#### 결정 5-3. 기아(starvation) 정책

| 선택지 | 장점 | 단점 |
|---|---|---|
| **[추천] a. 기본 rwlock 으로 먼저 측정** | 문제가 실제로 보일 때만 푼다 | 쓰기 100% / 읽기 90% 부하에서 INSERT 가 오래 밀릴 수 있다 |
| b. 쓰기 우선 속성 지정 (glibc 확장) | INSERT 가 굶지 않는다 | 이식성이 떨어진다 (Docker 환경에서는 허용) |

**추천 이유**: 문제가 측정에서 실제로 보일 때만 푼다. 추측으로 최적화하면 이식성만 잃는다.

> **[내 선택]** `미정` — 고르면 기호(`a`/`b`/`c` 등)와 사유를 여기에 적는다. `미정` 인 동안 위 추천은 참고일 뿐 결정이 아니다.

**완료 기준**
- S4 의 동시성 테스트(100 INSERT)가 그대로 통과
- **읽기·쓰기 혼합 테스트**: INSERT 와 SELECT 를 섞어 보내도 SELECT 결과가 항상 "완전한 행" 만 포함 (반쪽 줄이 보이지 않음)
- 읽기 90% 부하에서 S4 대비 처리량이 **측정으로** 증가 (S7 표에 사용)
- TSan 경고 없음

**하지 않는 것**: 테이블별 락, B+ 트리 노드 락

## 8. 팀이 먼저 정해야 할 열린 질문

위 추천 중 **다른 선택을 하면 이후 단계의 모양이 크게 바뀌는 것**만 골랐다.

1. **S0-3 (미리 열기)**: 서버 실행 중에 새 테이블을 만드는 기능이 필요한가? 필요하면 0-3 을 b 로 바꾸고 S5 의 읽기 락 근거가 달라진다.
2. **S2-4 (다문장)**: CLI 와 동작이 달라도 되는가? 같아야 한다면 2-4 를 c 로 올리고, "트랜잭션 없음" 을 문서에 명시해야 한다.
3. **S5-1 (엔진 수정 허용 범위)**: Phase 1·2 를 맡은 사람과 합의해서 `storage_scan` 의 `fflush` 를 옮겨도 되는가? 안 된다면 5-1 을 b 로 바꾼다.
4. **S7 (수치 중요도)**: 발표에서 성능 표가 핵심인가, 동시성 버그 재현·해결 과정이 핵심인가? 전자면 S5 에 시간을 더 쓰고, 후자면 S4 의 "락 뺀 빌드 재현" 을 더 공들인다.
