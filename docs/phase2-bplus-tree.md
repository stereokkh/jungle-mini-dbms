# Phase 2. B+ 트리 인덱스

테이블마다 메모리에 B+ 트리 하나를 둡니다. 키는 자동으로 붙는 `id`, 값은 그 행이 CSV 파일에서 시작하는 바이트 위치(offset)입니다. 행 자체는 트리에 넣지 않습니다. `SELECT ... WHERE id = 42`가 들어오면 트리에서 `42`의 offset을 찾고, `fseek`으로 그 자리에 가서 CSV 한 줄만 읽습니다.

## 실행 흐름

| 작업 | 처리 방식 |
| --- | --- |
| 테이블 열기 | CSV를 한 번 훑으며 가장 큰 id를 기억하고, 줄마다 `(id, offset)`을 트리에 넣습니다. 다음 id는 가장 큰 id + 1입니다. |
| `INSERT` | 다음 id를 붙여 CSV 끝에 한 줄을 쓰고, 그 줄의 offset을 id와 함께 트리에 넣습니다. |
| `WHERE id = 정수` | 컬럼·타입 검사를 거친 뒤 트리에서 id를 찾습니다. 있으면 그 offset의 한 줄을 읽고, 없으면 파일을 열지 않고 0행을 돌려줍니다. |
| 나머지 `SELECT` | 다른 컬럼 조건, `id >= N` 같은 범위 조건, `AND`·`OR`·`NOT`으로 묶인 조건은 전처럼 CSV 전체를 훑습니다. |

인덱스는 파일에 저장하지 않습니다. DB를 닫을 때 해제하고, 다음에 테이블을 열 때 CSV에서 다시 만듭니다.

## B+ 트리 구성

- **리프 노드**: 정렬된 id와 그 offset을 짝으로 담습니다. 리프끼리는 `next`로 왼쪽에서 오른쪽으로 이어집니다.
- **내부 노드**: 값 없이 길 안내 키와 자식 포인터만 담습니다. 키가 n개면 자식은 n+1개이고, 안내 키와 같은 id는 오른쪽 자식으로 내려갑니다.
- **노드 크기**: 노드 하나에 키를 최대 128개(`BPTREE_MAX_KEYS`) 담습니다. 100만 건이 3~4단계에 들어갑니다. id가 차례로 들어오면 나뉜 왼쪽 노드가 절반만 찬 채로 남아서 4단계가 됩니다.
- **분할**: 배열을 한 칸 크게 잡아, 꽉 찬 노드에도 일단 넣고 나서 둘로 나눕니다. 리프는 오른쪽 리프의 첫 키를 부모에 **복사**하고, 내부 노드는 가운데 키를 부모로 **옮깁니다**. 루트가 나뉘면 그 위에 새 루트를 얹습니다. 트리는 이때만 한 단계 자라므로 모든 리프의 깊이가 같습니다.
- **노드 안 탐색**: 노드 안에서는 앞에서부터 한 칸씩 비교합니다. 조회 시간의 대부분은 파일을 열고 한 줄을 읽는 데 들어서, 이진 탐색으로 바꿔도 차이가 거의 없습니다.

## 실패 처리

`bptree_insert`는 무슨 일이 있었는지만 `BPTreeStatus`로 알려 주고, 어떻게 할지는 부른 쪽이 정합니다.

| 결과 | 언제 | 처리 |
| --- | --- | --- |
| `BPTREE_OK` | 넣었다 | |
| `BPTREE_DUPLICATE` | 이미 있는 id다 | 테이블을 열 때 나오면 **깨진 파일**로 보고 `duplicate id N at offset M` 오류를 냅니다. INSERT에서 나오면 코드 버그라 `assert`로 멈춥니다. |
| `BPTREE_NO_MEMORY` | 노드를 만들 메모리가 없다 | 인덱스를 버리고(`db_drop_index`) 그 테이블은 선형 탐색으로만 조회합니다. 결과는 틀리지 않고 느려지기만 합니다. |

- **실패해도 트리는 그대로입니다.** 나눌 때 필요한 새 노드는 트리를 바꾸기 *전에* 미리 만들어 둡니다. 내려가는 길에 꽉 찬 노드를 만날 때마다 오른쪽 노드를 하나씩 만들고, 루트가 꽉 찼으면 새 루트도 만듭니다. 결국 나뉘지 않아 쓰지 않은 노드는 해제합니다.
- **중복 id는 정상적으로는 생기지 않습니다.** id는 `next_id`에서만 나오기 때문입니다. 생기는 경우는 CSV를 손으로 고쳤을 때뿐이라, Phase 1에서 깨진 줄을 오류로 보는 것과 같은 정책을 따릅니다.
- **메모리 부족은 INSERT 도중에도 생길 수 있습니다.** 행은 이미 파일에 쓰였으므로 INSERT는 성공으로 돌려주고, 이 행이 빠진 인덱스를 쓰지 않도록 인덱스를 버립니다. 이 상태는 `Table.index_usable`이 0인 것으로 표시합니다.

## 주의

**서버나 CLI가 실행 중일 때 CSV 파일을 직접 고치지 않습니다.** 메모리에 있는 인덱스의 offset과 `next_id`가 파일과 어긋나서, 엉뚱한 줄을 읽거나 같은 id를 다시 쓰게 됩니다. 고친 내용 중 중복 id는 다음에 테이블을 열 때 오류로 잡힙니다.

## 코드 읽는 순서

1. [executor.c](../src/executor.c)의 `run_insert`, `is_id_lookup`, `run_select`: SQL 실행기가 인덱스를 쓰는 곳
2. [bptree.c](../src/bptree.c)의 `bptree_search`, `bptree_insert`, `insert_into`, `split_leaf`, `split_internal`: 검색과 분할
3. [storage.c](../src/storage.c)의 `storage_append`, `storage_read_at`: offset을 얻고 쓰는 곳
4. [db.c](../src/db.c)의 `open_table`, `load_row`, `db_drop_index`: 테이블을 열 때 인덱스를 만들고 버리는 곳

## 테스트와 성능 비교

```sh
docker compose run --rm dev make test       # 분할, 검색, 중복, 다시 연 뒤 조회
docker compose run --rm dev make asan       # AddressSanitizer/UBSan, 메모리 누수 검사
docker compose run --rm dev sh bench/run.sh # 100만 건 비교 (행 수를 인자로 바꿀 수 있다)
```

[bench/run.sh](../bench/run.sh)는 CLI에 SQL 파일을 넣어 잽니다. CLI는 실행할 때마다 인덱스를 다시 만들기 때문에, 테이블만 여는 실행 시간을 빼고 질의 수로 나눠 질의 하나의 시간을 구합니다.

| 항목 (100만 건, 한 번 실행한 값) | 결과 |
| --- | ---: |
| INSERT 100만 건 | 2.3초 |
| 테이블 열기 (파일 훑기 + 인덱스 만들기) | 212ms |
| `WHERE id = N` (인덱스) | 질의당 약 24µs |
| `WHERE name = '...'` (선형 탐색) | 질의당 약 69ms |
| `WHERE id >= N AND id <= N` (선형 탐색) | 질의당 약 72ms |

측정값은 실행 환경에 따라 달라집니다.

## 하지 않은 것

- 삭제: DELETE 문이 없습니다.
- 인덱스 파일 저장: 테이블을 열 때마다 CSV에서 다시 만듭니다.
- 범위 조회: 리프가 `next`로 이어져 있어 만들 수 있지만, `id >= N`은 아직 선형 탐색입니다.
- 메모리 부족 경로 테스트: `malloc`을 일부러 실패하게 만드는 장치가 없습니다.
