## TL;DR
- `CDH/dbms` 에 Phase 3 API 서버 완성: 베이스 HTTP → JSON-RPC 2.0 SQL API → 스레드 풀 + 테이블별 rwlock → 우아한 종료 + 성능 비교. 엔진은 루트 `src/` 그대로 재사용(0줄 수정).
- 배운 핵심: `send`/`recv` 는 커널 버퍼 복사(HTTP 는 우리 코드가 만든 글자), REST vs RPC, 스레드 풀 = 생산자-소비자 큐, rwlock(읽기 공유·쓰기 독점), 시그널 마스크, 암달의 법칙.
- 성능: scan 은 작업자 1→8 에 916.8 ms → 136.8 ms(6.7배). lookup·insert 는 DB 일이 거의 없어 연결 처리·클라이언트 수가 상한 → 안 빨라짐. "insert 는 쓰기 락 때문" 은 틀린 설명이었음(측정으로 반증).
- 테스트: 단위 3개 + e2e 27개 + ThreadSanitizer 경고 0. 커밋만, 머지·PR 없음.

## 핵심 개념 정리

### send / recv 와 커널 (사이드 4)
- 정의: `send` 는 우리 함수 아님 → **리눅스 커널 시스템 콜**(glibc 래퍼, 내부적으로 `sendto`).
- 핵심 포인트:
  - `send` = "보냈다" 가 아니라 **"커널 송신 버퍼에 복사했다"**. 실제 전송·재전송·순서는 커널 TCP 가 비동기로.
  - 일부만 복사될 수 있음 → `send_all` 이 반복문. `recv` 도 일부만 올 수 있음 → `http_read_request` 반복.
  - 버퍼 꽉 차면 블로킹 → 반복 서버는 그동안 다른 연결 못 받음 → 스레드 풀 필요 이유.
  - 반환: `>0` 복사된 바이트, `-1`+errno(`EINTR` 재시도, `EPIPE` 상대 끊김, `ECONNRESET` RST).
  - `MSG_NOSIGNAL`: 끊긴 연결에 send 시 `SIGPIPE`(기본 = 프로세스 종료) 대신 `-1/EPIPE`.
  - `send(fd, …)` 에 주소 없음 → `accept` 때 커널이 fd 에 상대 IP·포트를 묶어 둠.
- 계층: HTTP(요청 줄·헤더·본문) = **우리 코드**(`http_parse`, `http_send_json`) / TCP·IP·랜카드 = 커널.
- 헷갈렸던 점: 내 이해 "send 하면 리눅스가 HTTP 로 보내 줌" → 실제: 커널은 바이트만 전달, HTTP 는 우리가 글자로 만든 것. 같은 send 로 RESP 를 보내도 커널은 똑같이 전달.
- 확인 방법: `strace -e trace=sendto,recvfrom ./build/dbms-server 18080`

### 실행 환경: Windows 가 아니라 Docker 안 리눅스 (사이드 4)
- 구조: Windows 11 → Docker Desktop → WSL2(진짜 리눅스 커널) → 컨테이너 `jungle-mini-dbms-dev`(Debian + gcc 13) → `build/dbms-server`.
- Windows 엔 gcc·make 없음. 소스는 `D:\Krafton\...` 를 컨테이너가 마운트.
- `<sys/socket.h>`, `sigaction`, `SIGPIPE` = POSIX API → Windows 네이티브(Winsock, `WSAStartup`)에선 그대로 컴파일 안 됨.
- 직접 실행: `docker compose run --rm dev bash` → `cd CDH/dbms && make && ./build/dbms-server 8080`. 포트를 밖에 안 열어서 Windows 에서 접속하려면 `compose.yaml` 에 `ports: ["8080:8080"]` 필요.
- 헷갈렸던 점: 내 이해 "윈도우에서 도는 것" → 실제: Docker 속 리눅스 커널이 소켓 처리.

### HTTP 헤더·본문 따로 보내기 (사이드 3)
- 꼭 따로일 필요 없음. TCP 는 바이트가 이어서 오므로 클라이언트 결과 동일.
- 따로 보내면 head 용 작은 버퍼(256B)만 필요, 큰 JSON 복사 안 함. 단점은 send 2번(무시 가능).
- 받을 때 헤더 안 보임 → curl 은 기본으로 본문만 보여 줌. `curl -i localhost:8080/health` 로 확인.
- 서버도 요청 헤더 중 `Content-Length` 만 꺼내고 나머지는 버림(일부러 단순하게).

### mini-redis 와 비교 (사이드 5)
| | mini-redis | mini-dbms |
|---|---|---|
| 전송 | TCP | TCP |
| 프로토콜 | RESP(`resp.c`, `redis-cli`) | HTTP/1.1 + JSON(`curl`) |
| 동시 처리 | `poll()` 이벤트 루프, 스레드 1개 | 반복 서버 → 3단계 스레드 풀 |
- 공통: `socket → SO_REUSEADDR → bind → listen`.

### REST(경로+메서드) vs RPC(함수 이름+인자) (사이드 5, 9)
| | HTTP API(`/query`) | RPC(JSON-RPC) |
|---|---|---|
| 요청 중심 | 경로 + 메서드 | `method` 이름 + `params` |
| 라우팅 | `route()` 경로 | `call_method` 이름 |
| 오류 | HTTP 상태(400/404/500) | 항상 200, 본문 `error.code` |
| 요청 짝 | 없음 | `id` 로 매칭 |
| 정의 | 문서 약속 | gRPC 는 `.proto` + 코드 생성, Protobuf + HTTP/2 |
- `POST /query` 도 사실상 `query(sql)` 함수 하나 → 정확히는 "HTTP 위의 RPC 스타일 API". 진짜 REST 는 `GET /users/1` 처럼 자원별 경로.
- RESP 의 `SET key value` 도 RPC 쪽.

### JSON-RPC 2.0 규칙 (메인, 사이드 9)
- 요청 `{"jsonrpc":"2.0","method":"query","params":{"sql":"..."}|["..."],"id":1}` → `{"jsonrpc":"2.0","result":{"results":[...]},"id":1}`.
- 표준 코드: -32700 parse error, -32600 invalid request(배치 포함), -32601 method not found, -32602 invalid params, -32603 internal. 서버 정의(-32000~-32099): -32001 SQL, -32002 테이블 없음, -32003 저장소.
- RPC 오류도 HTTP 200. `id` 없으면 알림 → HTTP 204. id 는 원문 그대로 반사. 배치 `[...]` 미지원.
- `data.executed` = 오류 전 실행된 문장 수(엔진에 트랜잭션 없음 → 되돌리지 않음).
- 요청 JSON 을 **읽어야** 해서 `json.c`(재귀 하강, `\uXXXX`→UTF-8, 서로게이트 쌍, `\u0000` 거절, 깊이 32) 추가.
- 바뀐 계층: `main.c → rpc.c(json.c) → query.c → 엔진`. `query.c` 는 오류 정보(`QueryError`)만 주고 응답 모양은 `rpc.c` 가 만듦 → RPC 를 바꿔도 query·엔진 무관.

### DB 는 언제 열리나 / 값은 어디서 읽나 (사이드 8, 9)
- `db_open`: 서버 시작 시. 파일 안 열고 데이터 폴더 경로만 `g_db` 에 저장.
- `db_get_table`(엔진 `src/db.c`): 테이블 **처음 쓸 때** `users.schema` 읽기 → `users.csv` 전체 훑어 B+ 트리·`next_id` → 데이터 파일 `"ab"` 로 열어 둠.
- `db_close`: 종료 시 파일 닫고 인덱스 해제.
- DB 엔진은 **기존 것**(루트 `src/`, Phase 1·2) 그대로. Makefile 이 `../../src/*.c`(CLI `main.c` 제외) 링크. `make run` 은 루트 `data/` 사용. 테스트는 `/tmp` 임시 폴더.
- SELECT 경로: `query.c run_statement` → `executor.c execute` → `db_get_table` → `run_select` → `is_id_lookup`?
  - 예(`WHERE id = 정수` 하나) → `bptree_search`(id→offset) → `storage_read_at`(그 줄만)
  - 아니오 → `storage_scan`(처음부터 끝까지)
  - 줄마다 `select_row`(WHERE 검사, 컬럼 고르기) → `on_row` 콜백 → JSON.
- 디스크에서 값 읽는 함수는 `storage_read_at`, `storage_scan` 둘뿐. 서버는 직접 안 읽음.

### 동시성 설계: 테이블 담당 스레드 vs 테이블 rwlock (메인)
- 사용자 제안: 테이블마다 담당 스레드 → 락 불필요, 대신 동시 읽기 불가.
- 답:
  - 장점: 엔진 데이터에 락 0, INSERT 순서 자연 보장. (Redis·VoltDB 계열)
  - 단점: 같은 테이블 SELECT 도 줄 섬(users 하나면 사실상 반복 서버). 락이 **작업 큐로 옮겨 감**(mutex+condvar) + 결과 전달 장치 필요. 테이블을 알려면 SQL 먼저 파싱. `Db.tables` 등록에도 결국 락.
  - 비교: A 전역 mutex(동시 읽기 ✗, 코드 최소) / **B 테이블 rwlock(동시 읽기 ✓, 짧음)** / C 담당 스레드(✗, 큼).
- 결정: B. C 는 README "다른 설계안" 으로 기록.
- 핵심 구현 포인트:
  - 락은 엔진 밖 `query.c`(엔진 무수정). `g_catalog`(테이블 목록) + `g_table_locks[i]`.
  - SELECT = 읽기 락(여럿 동시), INSERT = 쓰기 락(혼자) → `next_id`·B+ 트리·파일 끝 쓰기 보호.
  - 락 순서 항상 `g_catalog` → 테이블 → 교착 없음. 문장 단위(트랜잭션 아님).
  - 쓰기 우선(`PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP`) → 읽기 폭주 시 INSERT 기아 방지.
  - SELECT 의 `fflush(t->fp)`: INSERT 가 이미 비워 둠 + FILE 자체 락 → 읽기 락끼리 안전. SELECT 는 매번 따로 `fopen`.
  - `pthread_once` 로 락 1회 초기화.

### 스레드 풀 (메인, 사이드 6·10)
- 구조(생산자-소비자): main 은 `accept` → `pool_submit`(큐) / 작업자 N 개가 `pthread_cond_wait` 로 기다렸다 꺼내 `handle_client`. **handler 는 락 밖에서** 호출.
- 큐 64 꽉 차면 503(블로킹 대신 즉시 거절).
- 시그널: 작업자 생성 전 `pthread_sigmask` 로 SIGINT/SIGTERM 차단 → main 만 받음(작업자가 받으면 `accept` 가 안 깨어남).
- 요청 버퍼: `static` 공유 → 작업자 스택 64KB 로.
- 워커 수(사이드 10): IOCP 는 비동기 I/O 라 워커가 CPU만 써서 **코어 수**가 정석. 이 서버는 블로킹(`recv` 최대 5초, `fopen/fgets/fflush`, rwlock 대기) → 코어보다 많게. 공식 `스레드 수 ≈ 코어 수 × (1 + 대기/계산)`. 추천: `sysconf(_SC_NPROCESSORS_ONLN) × 2`(미적용). 리눅스 대응: `epoll`(준비 알림), `io_uring`(완료 알림, IOCP 와 가장 비슷).
- 헷갈렸던 점: 내 이해 "워커 = 코어 수" → 실제: 비동기 I/O 일 때만. 블로킹이면 더 많이.

### 카프카 / 메시지 큐 vs 로드 밸런서 (사이드 6)
- 카프카: 메시지를 디스크 로그 **끝에만 추가**하고 소비자가 각자 offset 으로 읽음. Producer / Broker / Topic / Partition(병렬) / Consumer. 비동기, 읽어도 안 지워짐, 파티션·브로커로 확장. LinkedIn 이 만듦.
- JSON-RPC(동기, 즉시 결과) vs 카프카(비동기, 로그 수집·이벤트 전달).
- 우리 엔진의 CSV 끝에 INSERT 붙이기 = 카프카 append-only 로그와 같은 생각. id ≈ offset.
- 메시지 큐 vs 로드 밸런서:
  | | 메시지 큐 | 로드 밸런서 |
  |---|---|---|
  | 동작 | 쌓았다가 일꾼이 꺼내 감(pull) | 바로 서버 하나로 넘김(push) |
  | 응답 | 안 기다림(비동기) | 기다림(동기) |
  | 서버 죽으면 | 일은 큐에 남음 | 그 요청 실패 |
  | 몰리면 | 큐가 흡수 | 느려지거나 오류 |
- 우리 스레드 풀 = 둘 섞음: 내부 큐 + 작업자 pull(큐 구조), 클라이언트는 응답 기다림(동기), 꽉 차면 503.

### 테스트 종류: 단위 vs e2e (메인)
- 단위(`make test`): 함수 하나 직접 호출(`http_parse`, `query_run`, `rpc_handle`) → 함수 안 논리 오류.
- e2e(`make e2e`, End-to-End): 서버를 실제로 띄우고 curl → 소켓→HTTP→JSON-RPC→SQL→엔진→파일 전체. 포트·시그널·스레드·파일 저장 같은 연결 오류.
- 비유: 단위 = 부품 확인, e2e = 조립한 완성품이 진짜 도나.

### 우아한 종료 (메인 4단계)
- Ctrl+C → `accept` 중단·리스닝 소켓 닫기(새 연결 거절) → `pool_stop`(처리·대기 중 요청 끝까지 + `pthread_join`) → `db_close` → 종료 코드 0.
- 덜 보낸 손님은 `TIMEOUT_SEC`(5초) 뒤 408 → 종료가 영원히 안 걸림.
- 두 번째 Ctrl+C = `_exit(130)` 강제(130 = 128 + SIGINT, `_exit` 는 시그널 핸들러에서 안전).

### 성능: 왜 작업자 수의 배수로 안 빨라지나 (메인)
- 벤치(5만 줄, 클라이언트 16, 총 시간): scan 916.8 → 459.9 → 243.8 → 136.8 ms / lookup 72.1 → 45.9 → 44.2 → 53.8 ms / insert 62.3 → 53.4 → 53.6 → 52.5 ms (작업자 1/2/4/8).
- 원인 5개(측정 근거):
  1. **암달의 법칙**: 빨라지는 건 작업자 안의 일뿐. DB 일 ≈ 0 인 `WHERE id = 0` 180.4 ms ≈ lookup 187.5 ≈ insert 190.5 → 시간 대부분이 TCP 연결·`accept`·송수신·`close`.
  2. **클라이언트 한계**: 각 클라이언트는 응답 받아야 다음 요청. 작업자 8 고정, 클라이언트 4/16/64 → 468.8/187.4/103.2 ms. 작업자 CPU 660 ms / 187 ms → 8개 중 3.5개만 일함.
  3. **스레드 관리 비용**: 같은 일에 작업자 CPU 합 lookup 250 → 630 ms(요청당 12 → 31 μs), scan 1,710 → 2,040 ms(+19%). 문맥 교환, 큐 mutex·cond, 메모리 대역폭·캐시 공유.
  4. **`accept` 는 main 1개**: 실행 시간의 43~50% 바쁨 → 다음 병목.
  5. **scan 도 완전 비례 아님**: 클라이언트 32 기준 16 작업자 11.7배(효율 73%). 끝 무렵 일부 작업자 놀음. p99 ~15 ms 하한은 Docker(WSL2 VM) 스케줄링 추정.
- 헷갈렸던 점: README 초안 "insert 는 쓰기 락 때문" → 실제: 락 구간이 μs 라 병목 아님. 원인은 1·2번.
- 결론: 스레드 풀은 **요청 하나에 드는 일이 클수록** 효과 큼. 개선(범위 밖): keep-alive, `SO_REUSEPORT`, INSERT 묶기.

### 사이드 4: send 동작 원리
1. Q: send 는 내부 함수잖아, 어떻게 동작해? → A: 커널 시스템 콜, 커널 버퍼 복사, 부분 전송·블로킹·errno·`MSG_NOSIGNAL`, recv 도 같은 구조, `strace` 로 확인.

3. Q: send 하면 리눅스가 그 주소·포트로 HTTP 로 보내 주는 거지? → A: 반만 맞음. 주소·포트(TCP/IP)는 커널, HTTP 는 우리가 만든 글자. 계층표.
