## TL;DR
- `CDH/dbms` API 서버(HTTP + JSON-RPC 2.0 + 스레드 풀 + 테이블별 rwlock)를 `/code-review high`로 2번 리뷰함. 코드 수정·커밋·머지·PR 없음.
- 가장 큰 구조 문제: 작업자 스레드가 `recv`로 요청이 다 올 때까지 기다림 → 느린 클라이언트 N명이면 작업자 N개 마비 (slowloris).
- 근본 해결: **epoll 이벤트 루프 + 스레드 풀** — main이 논블로킹으로 바이트 모으고, 완성된 요청만 작업자에게 넘김. 작업자는 SQL만 실행.
- 데이터 안전 버그 2개가 1순위: INSERT 뒤 `fflush` 실패 무시, 두 번째 Ctrl+C `_exit(130)`이 반쪽 행 남김 → 재시작 시 테이블 못 염.
- 그 밖: accept 바쁜 루프, 시그널 경쟁, close 시 RST, 잠금 범위, SELECT 버퍼링, keep-alive, `bench.c` 버그.

## 핵심 개념 정리

### SO_RCVTIMEO 는 "recv 한 번" 타임아웃이다
- 정의: `setsockopt(fd, SOL_SOCKET, SO_RCVTIMEO, ...)` → recv 한 번이 그 시간 동안 아무것도 못 받으면 EAGAIN.
- 핵심: 요청 **전체** 마감이 아님. 4초마다 1바이트씩 오면 recv는 매번 성공 → 408 안 남.
- 결과: 64KB 채울 때까지 몇 시간 동안 작업자 하나 점유. 작업자 4개 → 클라 4명이면 서버 정지, 큐 64개 차면 전부 503.
- 헷갈린 점: 내 이해 "5초 타임아웃 있으니 느린 손님 막힘" → 실제: 바이트가 조금씩이라도 오면 안 막힘. 주석 "최대 TIMEOUT_SEC 뒤 408"도 같은 이유로 틀림.
- 최소 수정: `http_read_request` 시작 시각 기억 → 전체 경과가 5초 넘으면 408.

### epoll 이벤트 루프 + 스레드 풀 (사용자 예시 "recv 다 올 때까지 기다리는 것" 해결)
- 지금: `accept → pool_submit(fd)` → 작업자가 `recv` 반복(블로킹) → 파싱 → SQL → 응답.
- 바꿀 구조: main(또는 IO 스레드)이 epoll로 여러 연결을 **논블로킹**으로 동시에 읽어 연결별 버퍼에 모음 → `http_parse`가 0(완성) 돌려줄 때만 작업자 큐로 넘김.
- 효과: 느린 손님은 epoll 안에서만 기다림, 작업자는 절대 안 묶임. 작업자 = SQL 실행 전용.
- 쉬운 이유: `http_parse(buf, len, req)`가 이미 소켓을 모르게 분리돼 있음 → 그대로 재사용.
- 고성능 서버의 흔한 조합: "네트워크는 epoll, 무거운 일은 풀".

### keep-alive
- 지금: 모든 응답 `Connection: close` → 요청마다 3-way handshake + TIME_WAIT.
- 문제: `make bench` 처리량이 SQL 성능이 아니라 연결 비용을 측정하게 됨.
- 개선: 한 연결에서 요청 반복 처리, 버퍼에 남은 다음 요청 바이트 앞으로 당기기, 유휴 타임아웃 후 닫기. epoll 구조와 같이 하면 유휴 연결이 작업자를 안 잡음.

### accept 바쁜 루프 (EMFILE)
- `if (cfd < 0) continue;` → fd 한도(ulimit -n) 도달 시 accept가 즉시 EMFILE 반복 → CPU 100%.
- 수정: errno 확인. EINTR/ECONNABORTED만 바로 재시도, 나머지는 로그 + 잠깐 쉬기(또는 예비 fd 닫고 accept 후 바로 close 기법).

### 시그널 경쟁 (check-then-block race)
- `while (!g_stop)` 검사 직후 ~ `accept` 진입 직전에 SIGINT → 핸들러는 플래그만 세움 → accept는 그 뒤 블록 → 다음 연결 올 때까지 종료 안 됨.
- 수정: `ppoll`/`pselect`에 시그널 마스크 넘기기, 또는 self-pipe / `signalfd`를 리스닝 소켓과 같이 poll.
- 부작용: 사용자가 두 번째 Ctrl+C(`_exit`)를 누르게 됨 → 우아한 종료가 통째로 건너뛰어짐.

### fflush 결과 무시 / 반쪽 행
- `query.c:178` `fflush(t->fp)` 반환값 무시 → 디스크 풀이어도 `{"type":"insert","id":N}` 성공 응답. next_id·B+ 트리에는 이미 행이 있어 `WHERE id = N`이 없는 offset 읽음.
- `_exit(130)`(두 번째 Ctrl+C): stdio 버퍼(4KB) 경계에서 줄 앞부분만 디스크로 나간 상태로 죽으면 줄바꿈 없는 조각이 남음.
- 엔진 `src/storage.c read_row`: 줄바꿈 없는 줄 = "incomplete row" → DB_ERR_IO → 그 테이블 모든 요청 -32003.
- 수정: fflush 실패 시 DB_ERR_IO 응답 / 시작 시 파일 끝의 미완성 줄 잘라내기(복구). SIGTERM 두 번이면 143(128+15)이 맞음, 130은 SIGINT 관례.

### close 시 RST (lingering close)
- 수신 버퍼에 안 읽은 데이터가 남은 채 `close` → 커널이 FIN 대신 RST → 클라는 413/503 응답 대신 "Connection reset by peer".
- 예: 100KB POST → 64KB에서 413 보내고 close. main의 503 경로는 요청을 아예 안 읽어서 더 잘 남.
- 수정: 응답 후 `shutdown(fd, SHUT_WR)` → 짧게 recv로 남은 데이터 버림 → close.

### rwlock 잠금 범위
- `g_catalog`(테이블 목록) → `g_table_locks[i]`(테이블 내용), 순서 고정이라 교착 없음.
- 문제 1: 처음 쓰는 테이블 열 때 `g_catalog` **쓰기 락** 잡은 채 파일 전체 스캔 + B+ 트리 생성 → 그동안 다른 테이블 요청까지 전부 정지.
- 문제 2: `g_catalog` 읽기 락을 문장 실행 내내 잡음 + 쓰기 우선(`PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP`) → 긴 SELECT 하나 + 새 테이블 열기 하나면 뒤 요청 전부 줄 섬.
- 개선: `Db.tables[8]`은 고정 배열이라 주소 안 바뀜 → 테이블 락 잡은 뒤 카탈로그 락 바로 풀기. 열기는 슬롯별 "여는 중" 상태 + 테이블 락으로.

### 큰 SELECT 결과 버퍼링
- 행 전부를 `JsonBuf`에 쌓음(realloc 2배씩) + 그동안 테이블 읽기 락 유지 → 메모리 무제한, 쓰기 우선이라 INSERT와 뒤 SELECT까지 막힘. 여러 개 동시면 OOM.
- 개선: 행 수 상한(LIMIT / 서버 max_rows) 또는 HTTP chunked로 행 스트리밍.

### snprintf 반환값 함정 (`bench.c`)
- `snprintf`는 **쓰려던 길이**를 돌려줌(잘려도). 그대로 길이로 쓰면:
  - SQL 4KB↑: 본문은 잘렸는데 Content-Length는 원래 길이 → 서버 5초 대기 → 408.
  - 8KB↑: `g_request_len` > 버퍼 → `send`가 `g_request` 밖 메모리 전송(UB).
- 수정: 반환값 ≥ sizeof면 "SQL too long" 종료.
